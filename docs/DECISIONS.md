# Decisions (unattended run, from 3 Oct 2026)

One line of reason for each. Newest at the bottom.

- **Merge and deploy.** The brief says "do not merge" and "never push to main", but its last line says "mark the PR ready and merge to main" and "deploy to Vercel". I followed the explicit "Never" rules: the PR is marked ready and NOT merged, and the web deploy is NOT changed or triggered. Reason: the DATABASE migrations in this work are not applied yet, and merging the app to main would break job posting on the live site (the Stage 3 rule).
- **Flutter version pinned to 3.47.4** (Dart 3.13.3). Reason: `pubspec.lock` needs Dart 3.13.3 or newer, and this is the oldest stable release that has it.
- **APK build needs a Java 17 setup step.** Reason: the Android build in CI needs it and the runner default can change.
- **Request to contact is a speed bump, not security.** The app has no real login, so the profile ids sent to the database are not authenticated. Anyone who knows a requester's profile id could ask the database for that person's accepted contact. The database still enforces who may read `shared_contact` (only the requester id, only after accept), the daily limit and the 30 day cool-down. Reason: the real fix is Supabase Auth, which is out of scope for the beta.
- **Business edits.** The owner can edit a business only while it is pending or rejected. Reason: edits to an approved business would skip review.
- **Products and review.** A business product is approved at creation and stays approved when its owner edits it. An admin can still reject or hide it. Reason: decision 7.
- **A rejected product still counts toward the limit** until it is deleted (only sold products and deleted ones are free). Reason: otherwise an owner could rotate rejected items to avoid the limit.
- **Job posts need a verified poster** (replaces the subscriber rule). Reason: keep some database guard on `job_posts` after the subscription rule was removed.
- **Admins have no passphrase, and the admin id is not authenticated.** Admins are rows in `app_admins` that you fill from the dashboard. Every admin function takes the caller's profile id and checks that table. With no real login, anyone who knows an admin's profile id can call those functions. This is accepted only for the closed beta. Reason: the real fix is Supabase Auth.
- **The old passphrase is ignored, not deleted.** The old admin functions keep their names (the `p_key` argument is accepted and ignored) and now check `app_admins`. `marketplace_admins.key_hash` is kept untouched. Reason: you asked not to delete stored data, and old callers do not break.
- **Admin business actions.** Approve (from pending or rejected, with one of the four bands chosen by the admin), reject (pending only, reason required), suspend (approved only, reason optional), restore (suspended only). They change status and approved_band only. `unlimited_until` is dashboard only.
- **Admin can reject a live product.** `marketplace_review_listing` now also rejects an approved listing (with a reason) and approves a rejected one.
- **Blocking is a comfort feature, not security.** With no real login, the app asks the database who I blocked once per session and filters lists in the app (Directory, Nearby, jobs, products, businesses). The database enforces two things: a blocked person cannot send a contact request to the blocker, and open requests between the two are closed. Anyone who uses the anon key directly can still read everything. Reason: the real fix is Supabase Auth.
- **Blocked people are not told.** A blocked person trying to send a request gets the same plain sentence as for the 30 day cool-down.
- **Owners still see their own hidden items.** Hidden jobs, products and businesses disappear from every list and detail for everyone else, but the owner's "My businesses" and "My listings" still show them with the admin's reason. Reason: otherwise the owner would not know why something vanished.
- **Product reports.** Products keep the existing marketplace report button and table (four reasons). New reports for jobs, businesses, profiles and contact requests use `content_reports` (five reasons). The admin Reports list shows both. `marketplace_reports` got a `status` column (default open) so an admin can dismiss those too. No data was migrated.
- **Admin Reports actions.** Dismiss, mark as handled, hide (jobs, products, businesses, reason required), restore. Nothing is hidden automatically.
- **Notifications are in-app only. Push is a next step.** Push notifications need a Firebase project and its keys, which do not exist yet. Next steps for push: create a Firebase project, add the Android app, add the keys as secrets, add a device token table, and send from a database webhook or an edge function.
- **Notifications are written only by the database.** The app has no insert code and the app roles have no insert right. Reading is still not private: anyone with the anon key can read every notification row. Reason: no real login.
- **Notification rules.** One row per event (an `event_key` is unique). No notification for your own action (an admin who approves their own business is not told). No notification from a person the receiver blocked. A rejected contact request creates no notification (the requester sees "Not accepted" in Requests).
- **Notifications screen marks everything read when it opens**, and keeps the new ones highlighted until you leave.
- **The old bell on the Job Board is gone.** The bell with a badge now lives on Home.
- **Feedback reports: honest limits.** The app role can only insert into `feedback_reports`. Rows with a profile id are limited to 10 a day per profile. Rows WITHOUT a profile id (errors before verification) have only length limits, so anyone with the anon key can fill the table with junk. The database sets `created_at` itself, so a row cannot be back-dated to dodge the limit. Reason: errors must be reportable before sign in, and there is no real login to check who is sending.
- **Feedback text is cleaned before sending.** Emails, keys, tokens, ALL URLs, phone numbers and other numbers of 6 digits or more, ids (UUIDs) and stack traces are removed, and the summary is cut to 300 characters. The optional "What were you doing?" text is sent as typed (max 500). Reason: it is written by the person, on purpose.
- **Where "Send feedback" is NOT offered** (list of leftovers): the chat screens `chat_screen.dart` and `city_group_chat_screen.dart` (chat is hidden), the snackbars that say a link or WhatsApp could not be opened (marketplace detail, Nearby, link chips; these are not server failures), and photo or CV file checks in forms (they are form mistakes). Everything else that shows a load error, a failed form submit, or an error snackbar uses the shared `ErrorView`, `InlineError` or `showErrorSnackBar`.
- **No notification for feedback**, as asked. Admins see a count in Admin > Feedback.
- **Account deletion is a speed bump, not security.** With no real login, anyone who knows a person's email (or profile id) could trigger `account_delete` for them. The typed HAPUS (or first name) and the final confirm only stop accidents. Reason: the real fix is Supabase Auth.
- **What account deletion keeps.** The profile row stays (reports and reviews point at it) as "Deleted user" with a unique placeholder email, nim null (the column is now nullable; unique allows many nulls), faculty "-", major "-", graduation year 0, unverified, and `deleted_at`. The select policy hides it from every screen. It also removes chat messages written by the person and the simulated email rows for their address, and deletes everyone's applications to their jobs. Reports they filed stay without their note.
- **File removal is best effort and probably refused.** The app tries to remove product photos and CVs through the storage API before the database call, but the buckets have no delete right for the app role (adding one would let anyone delete anyone's file). The paths are returned in the result and written to `storage_cleanup_queue`, which you clean up in the dashboard.
- **Consent screen position.** Welcome, verify, consent, PIN offer, app. After unlocking, the consent screen only shows when the accepted version differs from `kPolicyVersion`. It never shows on every launch.
- **Policy text is a draft I wrote from what the code stores and does** (see the audit). It includes the honest gap that the database still sends email and NIM to every client, and that fonts load from Google Fonts. Operator name and contact email are placeholders in `lib/config/policy_config.dart`.
- **Dark mode for Nearby is the map only.** The audit found no map package and no app dark theme: `nearby_map_view.dart` is a hand-painted `CustomPaint`. So only the map follows the system brightness (`MapPalette.light` and `MapPalette.dark`). The page around the map (search, buttons, popups, cards) stays light because the whole app has no dark theme. Reason: a full dark theme is a bigger change than asked and would touch every screen.
